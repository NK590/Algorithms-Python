# Lazy Propagation (느리게 갱신되는 세그먼트 트리)

> **한 줄 요약**: **구간 전체에 같은 갱신**(더하기, 대입, 뒤집기)을 하는 질의를 `O(log n)`에 처리하는 세그먼트 트리. 구간을 완전히 덮는 노드에는 값만 즉시 고치고 "자식들에게도 이 갱신을 해야 한다"는 표시(lazy)를 남겨 두었다가, 자식을 들여다봐야 할 때에야 아래로 내려보낸다. 네 가지 약속(`op`, `apply`, `compose`, 항등원)만 정하면 구간 합·최솟값·최댓값 등에 같은 틀을 쓴다.

## 1. 언제 쓰나 (문제 신호)

- "구간 `[l, r]`의 모든 값에 `d`를 **더하라**" + "구간 합(최솟값, 최댓값)을 구하라"
- "구간을 모두 `v`로 **바꿔라**(대입)" + 구간 합 질의
- "구간의 스위치를 **뒤집어라**" + 켜진 개수 질의
- 구간 갱신이 **n번 이상** 일어나 하나씩 고치면 `O(nq)`로 느려질 때
- 구간 **더하기 + 구간 합**만이라면 [펜윅 트리](../fenwick-tree/) 두 개로 가볍게 풀 수 있다. 최솟값, 대입, 뒤집기처럼 펜윅 트리가 안 되는 경우에 이 방법을 쓴다.

## 2. 핵심 아이디어

**순진한 방법의 낭비**: 구간 갱신을 [세그먼트 트리](../segment-tree/)에서 리프마다 하면 `O(n)`입니다.

**게으른 갱신**: 갱신 구간을 **완전히 덮는 노드**를 만나면 그 노드의 값만 즉시 고치고(`apply`), 자식은 건드리지 않은 채 "이 노드 아래 전부에 `f`를 적용해야 함"이라는 표시를 `lazy[node]`에 남깁니다. 그 노드 아래를 나중에 들여다볼 때(일부만 겹치는 질의나 갱신) 비로소 표시를 두 자식에게 내려보냅니다(`push`).

- `tree[node]`는 **그 노드까지의 갱신은 모두 반영된** 값입니다. 조상에게 쌓여 있는 표시는 아직 반영되지 않았을 수 있으므로, 조상에서 내려올 때는 반드시 **먼저 `push`**.
- 갱신·질의 모두 구간을 일부만 덮는 노드에서 자식으로 내려가기 전에 `push`, 갱신은 내려갔다 돌아온 뒤 `tree[node] = op(왼쪽 자식, 오른쪽 자식)`로 다시 계산.

**네 가지를 정해야 한다**

| 이름 | 의미 | 구간 더하기 + 합 | 구간 더하기 + 최솟값 | 구간 대입 + 합 |
|---|---|---|---|---|
| `op(x, y)`, `identity` | 두 구간의 값을 합친다 | `x + y`, 0 | `min`, ∞ | `x + y`, 0 |
| `apply(f, x, length)` | 길이 `length`인 구간의 값 `x`에 갱신 `f`를 적용한 값 | `x + f·length` | `x + f` | `f·length` (`f`가 없으면 `x`) |
| `compose(f, g)` | `g`를 먼저, 그다음 `f`를 한 것과 같은 하나의 갱신 | `f + g` | `f + g` | `f` (`f`가 없으면 `g`) |
| `lazy_identity` | 아무것도 하지 않는 갱신 | 0 | 0 | `None` |

- **구간 합**에서는 길이가 필요합니다. 구간의 모든 값에 `d`를 더하면 합이 `d × 길이`만큼 늘기 때문입니다. **최솟값**은 길이와 무관하게 `d`만큼만 늡니다.
- **합성**은 두 갱신이 겹쳐 쌓일 때 쓰이고, 순서가 중요할 수 있습니다. 대입 후 더하기와 더하기 후 대입은 결과가 다릅니다. 대입 갱신에서는 **나중 갱신이 이깁니다**.
- 갱신을 `None`으로 표시하는 이유: 대입값 `0`과 "아무 갱신도 없음"을 구분해야 하기 때문입니다.

### 무엇을 저장하고 어떻게 움직이나

노드의 집계값은 즉시 최신으로 만들되 자식에게 전달할 갱신은 표시로 남깁니다. 자식으로 내려갈 때만 그 표시를 전달합니다. 저장하는 집계값, 갱신을 집계에 적용하는 함수, 두 갱신을 합성하는 함수를 별도로 정의합니다.

### 왜 이 방법이 맞는가

구간 전체를 같은 규칙으로 갱신한 효과를 길이와 요약값만으로 계산할 수 있어야 합니다. 새 갱신과 기존 표시의 합성은 실제 시간 순서를 보존해야 합니다. 부모 값을 읽거나 아래로 내려갈 때 표시를 반영하면 직접 모든 원소를 바꾼 상태와 동등합니다.

### 작은 예제로 검산하기

구간 합 12, 길이 3에 5를 더하면 새 합은 27입니다. 이후 2로 대입하면 합은 6이고, 반대로 먼저 대입하고 5를 더하면 21입니다. 더하기와 대입은 순서가 달라 결과가 달라지므로 단순 덧셈으로 표시를 합치면 안 됩니다.

## 3. 손으로 따라가기

### 구간 더하기 + 구간 합: `[1, 2, 3, 4, 5, 6, 7, 8]`, `update(2, 6, +10)`

트리 번호는 [세그먼트 트리](../segment-tree/)와 같습니다. 노드 5는 구간 `[2,4)`, 노드 6은 `[4,6)`입니다. `[2,6)`을 완전히 덮는 노드는 5와 6입니다.

| 단계 | 일어난 일 |
|---|---|
| 초기 | `tree[1..7] = [36, 10, 26, 3, 7, 11, 15]`, 리프 `1..8`, `lazy`는 모두 0 |
| 루트(1)에서 | `[0,8)`을 일부만 덮음 → `push`(표시 없음) → 두 자식으로 |
| 노드 2 (`[0,4)`) | 일부만 덮음 → 자식으로 |
| 노드 4 (`[0,2)`) | 겹치지 않음 → 그대로 |
| 노드 5 (`[2,4)`) | **완전히 덮음** → `tree[5] = 7 + 10·2 = 27`, `lazy[5] = 10` |
| 노드 2 복귀 | `tree[2] = tree[4] + tree[5] = 3 + 27 = 30` |
| 노드 3 → 노드 6 (`[4,6)`) | 완전히 덮음 → `tree[6] = 11 + 20 = 31`, `lazy[6] = 10` |
| 노드 7 | 겹치지 않음 |
| 복귀 | `tree[3] = 31 + 15 = 46`, `tree[1] = 30 + 46 = 76` |

갱신 후 `tree[1..7] = [76, 30, 46, 3, 27, 31, 15]`, `lazy[5] = lazy[6] = 10`, **리프는 아직 `1..8` 그대로**입니다. 리프 4개를 건드리지 않고 노드 2개만 고쳤습니다. 전체 합은 `36 + 10 × 4 = 76`.

### 이어지는 질의: `query(3, 5)` (`a[3] + a[4]`)

`[3,5)`는 노드 5(`[2,4)`)와 노드 6(`[4,6)`)을 **일부만** 덮으므로 두 노드의 표시를 아래로 내려보내야 합니다.

| 단계 | 일어난 일 |
|---|---|
| 노드 5 방문 | `[2,4)`를 일부만 덮음 → `push`: 리프 10, 11에 `+10` → 리프가 `3 → 13`, `4 → 14`, `lazy[5] = 0` |
| 노드 6 방문 | 같은 방식으로 리프 12, 13이 `5 → 15`, `6 → 16`, `lazy[6] = 0` |
| 결과 | 리프 11(`a[3] = 14`) + 리프 12(`a[4] = 15`) = **29** |

이 환경에서 확인한 질의 후 상태: 리프 `[1, 2, 13, 14, 15, 16, 7, 8]`, 모든 `lazy`가 0. 질의가 일부만 겹치는 노드에서만 내려가므로 한 질의에서 `push`가 일어나는 노드도 `O(log n)`개입니다.

### 합성 순서: 대입 vs 더하기

구간에 `+3` 이후 `=5`를 하면 합성은 "`=5`"(나중 것이 이긴다)입니다. `=5` 이후 `+3`이면 "`=8`"로 합쳐야 하는데, 위의 대입 전용 트리는 더하기를 받지 않습니다. 둘을 모두 지원하려면 갱신을 `(a, b)`(`x → a·x + b`) 형태의 아핀 변환으로 일반화해 `apply((a, b), x, length) = a·x + b·length`, `compose((a₁, b₁), (a₂, b₂)) = (a₁·a₂, a₁·b₂ + b₁)`, 항등 `(1, 0)`. [테스트](test_solution.py)의 `test_non_commutative_affine_updates`가 이 구성이 순진한 계산과 일치함을 확인합니다.

## 4. 구현

전체 코드는 [solution.py](solution.py)에 있습니다. 구간은 0부터 시작하는 반열린 `[left, right)`입니다.

```python
class LazySegmentTree:
    def __init__(self, values, op, identity, apply, compose, lazy_identity):
        ...                                  # tree, lazy 배열 (크기 2·size)

    def _apply_to_node(self, node, f, length):
        self.tree[node] = self.apply(f, self.tree[node], length)
        if node < self.size:                 # 내부 노드는 표시를 쌓아 둔다
            self.lazy[node] = self.compose(f, self.lazy[node])

    def _push(self, node, length):           # 표시를 두 자식에게 내려보낸다
        f = self.lazy[node]
        if f != self.lazy_identity:
            half = length // 2
            self._apply_to_node(2 * node, f, half)
            self._apply_to_node(2 * node + 1, f, half)
            self.lazy[node] = self.lazy_identity

    def _update(self, node, node_left, node_right, left, right, f):
        if right <= node_left or node_right <= left:
            return                           # 겹치지 않음
        if left <= node_left and node_right <= right:
            self._apply_to_node(node, f, node_right - node_left)   # 완전히 덮음: 표시만
            return
        self._push(node, node_right - node_left)                   # 일부만: 먼저 내려보내고
        mid = (node_left + node_right) // 2
        self._update(2 * node, node_left, mid, left, right, f)
        self._update(2 * node + 1, mid, node_right, left, right, f)
        self.tree[node] = self.op(self.tree[2 * node], self.tree[2 * node + 1])
```

- 편의 생성 함수: `range_add_range_sum(values)`, `range_add_range_min(values)`, `range_assign_range_sum(values)`. 모두 `update(left, right, f)`, `query(left, right)`, `get(index)`.
- 직접 실행하면 `N M K`, `N`개의 수, `M + K`개의 질의(`1 b c d`: `b`..`c`번째에 `d` 더하기, `2 b c`: 합)를 받아 합 질의의 결과를 출력합니다.

## 5. 복잡도와 입력 크기 가이드

- **시간**: 구간 갱신·구간 질의 각각 **O(log n)**, 구축 `O(n)`. 한 번의 연산에서 방문하는 노드가 `O(log n)`개이고 `push`는 방문한 노드마다 상수 시간. **공간 O(n)**(`tree`, `lazy` 각 `2 · size`). ([복잡도 치트시트](../../../docs/complexity-cheatsheet.md))
- 이 환경에서 측정한 값입니다(`n = 10⁵`, 구간 길이는 무작위).

| 작업 | 횟수 | 시간 |
|---|---|---|
| `LazySegmentTree` 구간 더하기 + 구간 합 (각 한 번씩) | 5만 쌍 | 2.1초 |
| `LazySegmentTree` 구간 더하기만 | 10만 번 | 3.0초 |
| `RangeAddFenwick` 구간 더하기 + 구간 합 | 5만 쌍 | 0.45초 |
| 순진한 방법: 구간의 원소마다 더하고 합산 | 500번 | 0.42초 |

- 순진한 방법은 연산 한 번에 약 0.8ms(평균 구간 길이가 수만)라서 5만 번이면 약 40초(위 측정에서 선형 증가로 **추정**)입니다. 게으른 갱신으로 20배 가까이 줄지만, 이 구현은 재귀라 파이썬에서 느립니다.
- 구간 더하기와 구간 합만이라면 [`RangeAddFenwick`](../fenwick-tree/)이 약 5배 빠릅니다. 대입·최솟값·뒤집기가 필요할 때 이 트리를 쓰세요.
- 질의가 10⁵~2·10⁵개를 넘으면 파이썬에서는 반복문(AtCoder Library 방식) 구현이 필요합니다. 이 저장소는 이해를 우선해 재귀로 보였습니다.

## 6. 자주 하는 실수

- **`push`를 빠뜨림**: 일부만 겹치는 노드에서 자식으로 내려가기 전에 표시를 내려보내지 않으면 자식이 최신이 아닙니다. 갱신과 질의 **둘 다**에 필요합니다.
- **갱신 후 부모를 다시 계산하지 않음**: 자식을 갱신한 뒤 `tree[node] = op(...)`.
- **합에서 길이를 빠뜨림**: `x + f`가 아니라 `x + f · length`. 자식에게 내려보낼 때 길이는 부모의 **절반**입니다.
- **합성 순서 오류**: `compose(f, g)`는 `g`를 먼저 하고 `f`를 나중에 한 결과입니다. 대입·아핀 갱신에서 순서를 바꾸면 틀립니다(더하기만 있으면 우연히 맞아 보이니 더 위험).
- **"갱신 없음"과 "0으로 갱신"을 구분하지 않음**: 대입에서 `0`을 항등으로 쓰면 `0` 대입이 사라집니다. `None`을 씁니다.
- **리프에 표시를 쌓음**: 리프는 자식이 없으므로 `lazy`를 저장하지 않습니다(`node < size`).
- **재귀 깊이**: `log n ≈ 20`이라 문제없지만 호출 횟수가 많아 느립니다.
- **최솟값 트리의 빈 칸**: 부족한 칸은 `+∞`로 두어야 하고 `∞ + f = ∞`로 안전합니다.
- **값을 읽을 때 `push`를 안 함**: `tree[leaf]`를 직접 읽지 말고 `query(i, i+1)`로 읽습니다.

## 7. 변형과 응용

- **구간 뒤집기 + 켜진 개수**: 갱신은 불리언 `flip`, `apply(f, x, length) = length − x if f else x`, `compose = xor`.
- **구간 XOR + 구간 XOR 합**: 갱신값 `d`, 구간 길이가 홀수일 때만 합이 `d`만큼 바뀐다.
- **구간 곱·더하기·대입 섞기**: 아핀 변환 `(a, b)`로 일반화(위의 예).
- **구간 최솟값 + 개수**: 노드에 (최솟값, 그 개수) 쌍을 저장.
- **느리게 갱신되는 동적 세그먼트 트리**: 좌표가 매우 클 때 필요한 노드만 만든다.
- **세그먼트 트리 비츠(Segment Tree Beats)**: `a[i] = min(a[i], x)` 같은 구간 갱신까지 지원하는 기법으로 Lv4 이상.
- **제곱근 분할**: 코드가 간단한 대안으로 `O(√n)`이다. → [제곱근 분할](../../06-query-techniques/sqrt-decomposition/)
